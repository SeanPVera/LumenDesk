# LumenDesk controls audit

Findings from an audit of every exposed control on the macOS/iOS app and the web client, tracing each one from the interaction through app state, the bridge where one exists, the protocol encoder, and the device reply.

Companion to the pull request that fixes the confirmed defects. See `README.md` for user-facing behaviour and `CLAUDE.md` for architecture.

## Prioritized defects fixed

| # | Severity | Defect | Surface |
|---|---|---|---|
| 1 | **Misleading success/failure** | LIFX colour commands can never confirm; false "did not confirm the change" after 3.5 s on nearly every colour and theme | Desktop |
| 2 | **Incorrect lighting** | Bridge colour command reverts a brightness set moments earlier (20% → 50%) | Web |
| 3 | **Misleading preview** | Scene rehearsal previews a solid wash where Apply paints Govee segments, and never sends Govee brightness | Desktop |
| 4 | **Silent data loss** | Configuration export fails silently; user believes they have a backup | Desktop |
| 5 | **Silent data loss** | White-mode per-light setting persists locally but drops out of every export | Desktop |
| 6 | **Misleading control** | Per-light colour/brightness/white accept changes an effect overwrites one frame later | Desktop |
| 7 | **Broken automation** | Bridge `updateSchedule` stores an empty weekday list, which its evaluator reads as "never" while the native engine reads it as "every day" | Web |
| 8 | **Abandoned state** | Web Music Mode Stop freezes the last frame on the lights forever | Web |
| 9 | **Unfounded state** | `/music/frame` records `power: true` for a path that sends no power command | Web |

## Web expansion: the smallest useful next feature

### Where the two clients stand today

| | Native | Bridge + web client |
|---|---|---|
| Govee per-segment **live** paint | `razer` streaming, volatile | none |
| Govee per-segment **durable** write | `ptReal` relaying 20-byte BLE packets | none |
| Govee stream-hold families (H60B0, string, curtain) | layout held and re-asserted every 30 s | none |
| LIFX Luna matrix | `GetDeviceChain` → `Get64` / `Set64`, 26 zones | none |
| Encoders present in the bridge | — | `scan`, `turn`, `brightness`, `colorwc`, `devStatus` only |

`web/bridge/src/govee.js` is 72 lines and stops at the five documented LAN commands. `lifx.js` has no `Set64`. So today a web scene captured on an RGBIC strip stores one blended colour, and web Music Mode washes a 15-segment strip in a single hue.

### Recommendation: port `razer` only, and ship a read-only-plus-live Segment Studio

**Do not** port `ptReal` in the first step. `razer` is one packet family, fully described by an existing byte-for-byte Swift test, and it is **volatile** — the worst outcome of a bug is a wrong colour until the overlay drops. `ptReal` writes durable state into firmware with no acknowledgement and no read-back; getting it wrong leaves a user's strip permanently wrong with no way for the bridge to detect it. Earn the second with the first.

**User experience.** A Govee RGBIC device gains a "Segments" panel in the web Devices view: a strip of N colour wells, a gradient toggle, and a live preview that streams while the panel is open. The panel states plainly that the layout is live-only and will fall away when the panel closes or the light is power-cycled, and that durable layouts still need the Mac app. Music Mode gains per-segment frames for the same devices.

**Supported devices.** Govee RGBIC models the native `GoveeSegmentProfile` catalog recognizes (H619x COB strips, H70Cx string lights, H60B0 lamp, curtain families). The bridge needs the SKU, which it already stores from the scan reply (`registry.upsert(..., {sku})`); `GoveeSegmentProfile.detect` has to be ported alongside so segment counts and the H60B0 two-of-three zone rule come with it.

### Changes required

**Protocol (`web/bridge/src/govee.js`)** — port three functions from `GoveeProtocol.swift`, unchanged in behaviour:
- `xorChecksum(bytes)`
- `razerModeRequest(on)` → `[0xBB, 0x00, 0x01, 0xB1, on ? 1 : 0, xor]`, base64 into `{"msg":{"cmd":"razer","data":{"pt":…}}}`
- `razerFrameRequest(colors, blend)` → `[0xBB, lenHi, lenLo, 0xB0, blend ? 0x00 : 0x01, count, …rgb triplets…, xor]`, colours capped at 255 and clamped 0–255

**Protocol tests (`web/bridge/test/protocol.test.js`)** — the lockstep rule in `CLAUDE.md` is the binding constraint. Add vectors byte-identical to the ones in `LumenDeskTests/ProtocolTests.swift` for both functions, in the same file that already does this for `colorRequest`. Changing `GoveeProtocol.swift` and `govee.js` out of step is what the rule exists to prevent.

**Bridge client (`web/bridge/src/govee-client.js`)**
- `setRazerMode(device, on)` and `sendRazerFrame(device, colors, blend)`, both through the existing `#enqueue` so the ≥100 ms pacing and same-kind coalescing apply unchanged. Frames coalesce under one kind key, so a 20 Hz stream collapses to the pacing ceiling exactly as the native `GoveeClient` does.
- Per-device `razerActive` bookkeeping mirroring `LightManager.razerActiveIDs`: enable mode once, forget it on power-off and on an address change.

**Bridge API (`web/bridge/src/server.js`)** — two routes, both under the existing `originPermitted` gate, which is what keeps this local-only:
- `POST /devices/<id>/segments/preview` `{colors: [{r,g,b}], gradient: bool}` — enables razer mode if needed and sends one frame. 400 on a malformed colour list, 503 when the device has no address, 409 for a non-Govee device.
- `POST /devices/<id>/segments/stop` — drops the overlay.
- Extend `/music/frame` to accept `{fixtureID, segments: [{r,g,b}]}` beside the existing `{fixtureID, rgb}`, routing segments to a razer frame and a plain rgb to `colorwc`. Keep the one-state-per-fixture dedupe.
- `GET /devices` / `/state` gain `segmentProfile` per device so the client knows the segment count and zone rules without a second round trip.

**Client (`web/app/src/`)** — a `SegmentPanel` in `views.tsx` plus `previewSegments`/`stopSegments` in `bridge.ts`. Music Mode's `frameToCommands` emits `segments` for fixtures whose profile has more than one segment.

### Reuse

- `LumenDeskTests/ProtocolTests.swift` already holds the razer vectors — the bridge test copies them rather than inventing any.
- `GoveeSegmentProfile.detect` and `enforcingZoneLimit` port directly from `Models/GoveeSegments.swift`; `DomainTests.testZoneLimitSwitchesOffTheZoneLitLongest` gives the expected outputs to assert against.
- `FakeGoveeDevice` already records every `cmd` it receives, so it can assert `razer` arrived — the rewritten music test in this PR asserts the inverse today and inverts cleanly.
- `#enqueue`/`#drain` need no change; they already pace and coalesce by kind.
- `zoneConstrained` in `LightManager` is the reference for keeping an H60B0's clamp stable frame to frame.

### Device limitations and unresolved assumptions

- **Volatile by design.** Razer layouts vanish on power-cycle and when the overlay drops. Not a bug to fix — the native app's stream-hold families exist precisely because that is all the firmware offers.
- **No acknowledgement.** Govee LAN sends no ack for `razer`. The bridge can report *sent*, never *confirmed* — it must use the same distinction the native `recordUnconfirmedSend` makes.
- **Unverified assumption:** that `razer` is accepted on the same UDP 4003 control port as `colorwc` on every SKU in the catalog. The native client sends it there and the community projects document it there, but **no SKU has been confirmed on hardware in this environment.**
- **Unverified assumption:** that a 20 Hz razer stream does not overrun firmware the 100 ms pacing was tuned for with single commands.
- **Unverified assumption:** that re-sending `razer-on` mid-session briefly clears the frame on H60B0 — the native code says so and works around it, but the workaround is not independently confirmed here.
- **Out of scope:** `ptReal`, and therefore durable web layouts, the 30 s stream-hold keepalive, and segment capture in web scenes.

### Acceptance criteria

1. `razerModeRequest` and `razerFrameRequest` produce bytes identical to `GoveeProtocol.swift` for every shared vector.
2. `POST /devices/<id>/segments/preview` with 15 colours makes `FakeGoveeDevice` receive exactly one `razer` mode command (first call only) and one `razer` frame per request.
3. `POST /devices/<id>/segments/stop` sends `razer` with the off payload and clears the local flag.
4. An H60B0 profile preview with three zones lit sends a frame with exactly two lit and one black, stable across ten consecutive frames.
5. A 20 Hz stream to one device produces datagrams no closer than 100 ms apart, with intermediate frames coalesced away.
6. `/music/frame` with `segments` sends a razer frame; with `rgb` sends `colorwc`; a fixture appearing twice is applied once.
7. A non-Govee device returns 409; a malformed colour list returns 400; a device with no address returns 503.
8. An unlisted origin cannot reach either route.
9. `/music/frame` never sends `ptReal` — the existing assertion stays and must keep passing.

### Automated tests

Extend `protocol.test.js` (vectors), `integration.test.js` (routes over real UDP against `FakeGoveeDevice`, pacing, zone clamp, origin gate), and add `segments.test.js` for the ported profile catalog. `FakeGoveeDevice` needs a `razerFrames` array and a `razerMode` flag so a test can assert the decoded packet rather than just the command name.

### Physical-hardware verification required

Software tests cannot establish any of this. Before shipping:

1. **Govee H619A (or another COB strip).** Preview a 15-segment rainbow. Photograph the strip. Confirm each segment matches its commanded colour and that the gradient toggle visibly blends versus holds hard edges.
2. **Same device.** Close the panel. Confirm the strip returns to its stored static layout within ~1 s — this is the volatility guarantee the whole design rests on.
3. **Same device.** Run web Music Mode for 60 s at 20 Hz. Confirm no dropped frames, no firmware lock-up, and no visible stutter the 100 ms pacing does not explain.
4. **Govee H60B0 uplighter.** Preview with all three zones lit. Confirm exactly two light and that the *same* two stay lit across a full minute rather than alternating.
5. **Same H60B0.** Confirm whether re-sending `razer-on` mid-stream blanks the frame, settling the assumption the native workaround is built on.
6. **Any RGBIC device with a durable layout applied from the Mac app.** Run a web preview, stop it, power-cycle the device, and confirm the durable layout is intact — proving the web path wrote nothing permanent.
7. **A Govee model the catalog does not recognize.** Confirm it either ignores razer packets harmlessly or is correctly excluded by the profile gate.
